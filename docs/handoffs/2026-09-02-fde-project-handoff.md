## 2. The headline finding — read this before anything else

**The written underwriting policy's DTI gate is not enforced in code, and no debt-log entry owns it.**

`policies/underwriting_guidelines.md:17-19` conditions all three bands on DTI as well as score:

- Approve: score ≥ 660 **and DTI ≤ 43%**
- Refer: score 600–659, **or DTI 43–50%**
- Deny: score < 600, **or DTI > 50%**, or fraud flag

`services/decision-service/app/model_vendor.py:76` implements `policy_band(score)` — it takes the score and
nothing else. DTI enters only as a smooth contribution to that score, via `payment_burden` in
`model_vendor.py:40`:

```python
payment_burden = max((0.35 - dti) * 120.0, -80.0)
```

**That floor is the defect.** DTI's total possible influence on the score is capped at −80 points, while the
other three features contribute up to +137 combined at their maxima: `delinquency_history` +105 (bureau 850),
`income_sufficiency` +20, `employment_tenure` +12. Floor score = 640 + 137 − 80 = **697**, which is above the
660 approve cutoff. So **no DTI value, however extreme, can move a strong-bureau application out of `approve`.**

Executed against the module as it ships (`bureau_score=850, annual_income=120000, requested_amount=24000,
term_months=60, employment_years=10`, varying `monthly_debt`):

| DTI | score | code band | written policy band |
|---|---|---|---|
| 0.60 | 747 | `approve` | deny (>50%) |
| 1.00 | 699 | `approve` | deny |
| 2.00 | 697 | `approve` | deny |

The break-even is `bureau_score` 776: at or above it, with income ratio and tenure at their maxima, the
application approves at **any** DTI (verified — 770 → 657 → `refer`, 776 → 660 → `approve`). DTI alone cannot
produce a `deny` at any input.

The module's own comment at `model_vendor.py:17` cites the policy file and transcribes only the score half of it.

**Why this matters for the incoming spec:** the target agent's §4 escalation trigger ("DTI between 43% and 45%")
rests entirely on a DTI band that this platform does not evaluate. Building the trigger on top of the current
scorecard would produce a control that never fires for the reason its author intended.

**Recommended first action for the incoming FDE:** open a debt entry for this — D40 was the last entry at base
`10d13ca`, so re-read the tail of `docs/debt-log.md` on `main` for the current last number before assigning one — and
decide with the client whether the fix is (a) enforce the policy file's DTI gate as a hard band alongside
`policy_band`, or (b) amend the policy file to describe the score-only behaviour that actually ships. Do not
build the §4 DTI trigger until that is settled — it would encode the ambiguity rather than resolve it.

## 3. Reconciliation — the incoming agent spec against what is on `main`

### §1 Identity: "autonomous AI Financial Lending Agent … generate structured loan recommendations"

**Conflicts with a locked design decision.** The built assistant is deliberately not autonomous. Per
`services/origination-service/app/assistant.py:1-19`: the regulated decision and its append-only
`decision_events` record happen **inside** the score tool in decision-service; the model orchestrates and
narrates but cannot decision an application without the record being written, cannot supply applicant data
(tools take an application id, lookups happen in code), and its final answer is validated against the persisted
record before it reaches an officer — on mismatch the recorded facts are returned, never the narration. The
officer-facing summary is code-constructed (`assistant.py::_constructed_summary`), which is why that path has no
groundedness gap.

Adopting §1 as written reverses ADR 0009 §5. That is a decision for the client and it needs an ADR, not a code
change. Flag it before writing anything.

### §2 Compliance — ECOA / FCRA / AML-KYC, no demographic data

**Partly holds.** The scorecard's inputs are `bureau_score`, `annual_income`, `requested_amount`, `term_months`,
`monthly_debt`, `employment_years` (`model_vendor.py:31-36`). No age, race, gender, or marital status reaches
the model.

Three caveats:

- The guarantee is by input selection, not by isolation. `applicants.dob` and `applicants.address` are stored
  (`db/init/001_schema.sql:23,33`) and every service shares one schema (ADR 0002), so nothing structurally
  prevents a future feature from reading them.
- Reg B adverse-action reasons **are** built and fail closed: `services/decision-service/app/reasons.py` raises
  `UnmappedFeatureError` and refuses the decision rather than issue a generic fallback reason.
- **Nothing measures disparate impact.** ADR 0016 (fair-lending monitoring computes outside the platform) is
  Proposed and not built. The Reg B effects test is still open on the regulator watch.

### §2 Data privacy — "never store plain-text SSNs"

**Violated today.** `db/init/001_schema.sql:24` — `ssn TEXT, -- plaintext`. This is debt D33.

What is built (ADR 0023 Decision 1, merged as PR #142 `25157e4`, held by the blocking `ssn-purge-gate` and a
`db-readiness-gate` rung): `applicants.ssn_last4`; intake and the recheck hop send kyc-service last-4 rather
than the full SSN; the purge CLI (`services/origination-service/app/purge_ssn.py`) carries a placeholder
interlock that refuses an `--execute` run.

What is not built: ADR 0023 Decision 2, the retention-contingent remediation. **It is blocked on a client answer
about retention duration.** Until that lands, `applicants.ssn` stays plaintext and nothing has been purged.

Log redaction is in better shape — D5 is Mitigated: `PiiRedactor` ships in all 7 services, kept identical by the
blocking `redactor-drift` job, covered by `redaction-tests`, with daily UTC rotation and 30-day retention held
by `log-rotation-gate`. Residuals: encoded PII bypasses the redactor (D14, deferred); nothing is encrypted in
transit anywhere (D35); pre-redaction logs and backups are unaudited (D38).

### §2 Limitations — "no signing authority above $50,000; may pre-approve below"

**Present as a different mechanism with different semantics.** `$50,000` is an input validation ceiling, not a
routing rule: `services/origination-service/app/schemas.py:54` and
`services/disclosure-service/app/schemas.py:17,122` all declare `Field(gt=0, le=50000)`. An application above
$50k is rejected with a 422 at intake — it never reaches a human underwriter, because it never exists.

The spec wants *route to a human above the line*. The code does *refuse above the line*. Reconciling those is a
schema change plus an escalation path, not a constant.

"Pre-approve subject to human verification" also has no state to land in. `decisions.outcome` is
`TEXT NOT NULL` with the vocabulary `'approve' | 'deny' | 'refer' | 'counteroffer'` recorded **only as a SQL
comment** (`db/init/001_schema.sql:97`) — there is no CHECK constraint. `refer` is the nearest existing thing to
the spec's `ESCALATED`. See also debt **D4**: the outcome-only `decisions` table is still the one the offer path
reads.

### §3 Tool contracts

The spec names three tools. The agent that exists has three tools, and **none of the names match**:

```
_TOOLS = {                                    # assistant.py:257
    "score_application": _score_application,
    "get_decision_record": _get_decision_record,
    "search_policy": _search_policy,
}
```

- **`verify_kyc_aml(applicant_id)` — not buildable on the current kyc-service.** That service is CIP only. It
  performs no OFAC or sanctions screening, captures no beneficial owner, does no ongoing monitoring and has no
  SAR path (`services/kyc-service/app/kyc.py:6-14`, `services/kyc-service/app/routers/kyc.py:3-6`,
  `db/init/001_schema.sql:82,90`). `sanctions_screened=False` is written as a hardcoded literal at
  `services/kyc-service/app/routers/kyc.py:108`. There is a deliberate, documented *absence* of a test for it
  (`services/kyc-service/tests/test_cip.py:3`).

  **A trap worth knowing:** this gap is cited throughout the code as "debt D11", and `docs/debt-log.md` does not
  define a D11. The log says so itself at `docs/debt-log.md:71-75` — code cites `D3`, `D4`, `D7`, `D11`, `D12`,
  `D14`; the log defines `D14` as something else and leaves the `D7`/`D11`/`D12` collisions alone. So the single
  largest dependency of the incoming spec's AML tool is recorded **only in code comments, under a number the
  debt log does not resolve.** Give it a real entry before you plan against it.

- **`fetch_credit_score(applicant_id)` — partially exists, returns less than the contract promises.**
  decision-service pulls a score and labels its provenance honestly:
  `bureau_verified` / `synthetic_credit` / `synthetic_credit_bureau_failed`
  (`reasons.py::CREDIT_SOURCE_PROVENANCE`), held by the blocking `synthetic-credit-gate`. It returns a score.
  There are **no active trade lines** anywhere in the schema, and DTI is not returned — see the next item.
  Related: debt **D26** — three of the four scored features are unverified applicant assertions.

- **`calculate_affordability(...)` — does not exist as a callable anything.** The DTI computation is inline
  inside the scorecard at `model_vendor.py:40` and is not exposed, not tested as a unit, and not reusable.

### §4 Escalation triggers

| Spec trigger | State on `main` |
|---|---|
| DTI exactly borderline (43–45%) | **No such band exists in code.** See §2 of this document — `policy_band()` is score-only and the policy file's DTI gate is unenforced. |
| KYC returns "Flagged" or "Inconclusive" | **No such status exists.** `services/kyc-service/app/schemas.py:28` — `status: str  # "pass" \| "fail"`. Two-valued. There is nowhere to put an inconclusive result. |
| Any API returns 5xx or times out | **Detection exists; escalation does not.** `services/origination-service/app/clients.py:99-114` classifies 5xx and timeouts and trips a circuit breaker. Timeouts are nested correctly since D28's partial fix — origination's module-level 30s outer budget against decision-service's strictly smaller 20s bureau pull, so a stall is attributable to a hop. But the outcome is an error returned to the applicant, **not a handoff of session state to an underwriter.** There is no underwriter queue for system-error escalations. D28's remaining residuals: no connect/read timeout split, no per-class retry policy, no deadline propagation. |

### §5 State management and output schema

None of `risk_tier`, `compliance_verified`, or `requires_human_review` exist in any table or response model.

There are two audit surfaces, and they are shaped differently from what §5 asks for:

- `decision_events` (`db/init/001_schema.sql:216`) — append-only, the regulated record.
- `assistant_runs` (`db/init/001_schema.sql:472`, migration `db/migrations/0021_assistant_runs.sql`) — agent
  telemetry: trace id, application id, task, policy topic, http status, refusal code, outcome, record status,
  policy band, narration validated, citation and search counts, latency. `task` carries a CHECK constraint
  (`'decision' | 'explain'`); **`outcome` and `policy_band` carry none.** The officer-gated
  `GET /assistant/metrics` is that table's only export boundary, and its closed vocabulary mask is the only
  thing keeping an unconstrained write off an officer's screen. Held by the blocking `assistant-telemetry-gate`.
  The telemetry write is swallowed on failure by design, so nothing at runtime reports a volume whose migration
  never ran — which is why that gate runs migration 0021 against a real Postgres.

4. **The reconciliation alert threshold, and who receives the alert.** `alert_triggered` is a computed boolean
   on the report (`services/servicing-service/app/reconciliation.py:251`), gated on

   mechanism at all**: no email, webhook or pager exists in the service. The alert surfaces only as a field in
   the JSON report on stdout and in the CLI exit code, so it reaches a human only if one runs the CLI and reads
   the output. This has been asked twice and is still open.

6. **Whether the agent is autonomous at all** — new, from §3 §1 of this document. This one is an ADR.

## 5. Operating rules the incoming FDE must not break

**Ground-truth before you fix.** For any review comment or claimed defect: verify against local code and say
VALID or INVALID with `file:line` evidence before touching anything. The `address-pr` skill automates the loop.

**Prove before fix.** Write the regression test, watch it fail, then fix. `make prove` rolls the source back to
the parent commit and requires the test to FAIL without the fix and PASS with it. It aborts on a dirty tree —
run it from a detached worktree, never stash someone's work. It is pytest-only; a `.tsx` change cannot be proven
this way and must be demonstrated by hand.

**The CI tolerance is narrower than it looks.** The `backend` matrix runs pytest under `continue-on-error` plus
`|| true`, so money-math failures there do not block. But the `Import smoke` step in that same job **does**
block, and every control that must not regress has its own blocking job — see the CI section of `CLAUDE.md` for the
enumerated list. Among them: `redactor-drift`, `redaction-tests`, `tila-vectors-gate`, `synthetic-credit-gate`, `atomic-apply-gate`,
`reconciliation-gate`, `payment-idempotency-gate`, `ssn-purge-gate`, `agentic-loop-gate`,
`assistant-telemetry-gate`, `secret-scan`, and the four doc lints. Read that section before adding, splitting or
reordering anything. A failed blocking gate is a wasted review round.

**Two combined tolerances hide a red test completely:** `|| true` in the matrix *plus* a blocking gate's by-name
`-k` exclusion. The exclusion's comment rots too. If you exclude a test by name from a gate, expect nobody to
notice it is red.

**A green local run proves nothing about dependencies.** Steps in one CI job share a Python environment, so a
service that under-declares its requirements can pass on a package an unrelated earlier step installed. Verify
in a fresh venv with the gate's exact install line.

**Never hand-edit `docs/state.md`.** Run `make kb`. The blocking `kb-freshness` job grades it against the
branch's merge base, and `make kb` must run *after* the merge commit or it silently drops the PR's own job rows.

**Never write a decaying sentence into `README.md`, `CLAUDE.md` or `docs/kb.md`.** No open-PR claims, no "not on
`main` yet", no tip shas, no spelled-out counts of a growing set. The blocking `volatile-claim-lint` refuses the
whole class. An immutable citation passes: "merged as #77 (`ceda4e2`)" names a merge commit, and a merge commit
never changes. The escape hatch `<!-- VOLATILE-OK: reason -->` is audited — a marker on a line that no longer
violates anything fails, so it cannot rot open.

**Debt-log status vocabulary is load-bearing.** *Mitigated* means the control ships and something blocking keeps
it from regressing. *Fixed* means every row of that entry's Mitigation Path is done. Never describe work as
sitting in an unmerged PR — D5 carried that false claim in three places for five weeks after merging. Verify
with `git merge-base --is-ancestor <branch> <base>`; a branch existing locally proves nothing.

**Working agreement on PR size.** Maximum two open PRs; a third requires closing one. Target median merged PR at
or under 400 changed lines, hard cap 800. Split at seams that ship something whole, before review starts, and
keep code and tests together. A PR that is still growing is not a PR — PR #12 grew 65% *after* the instruction
to stop amending it.

**Branch naming.** `<type>/<slug>[-week<N>]`, Conventional Commits type, `feat` never `feature`, slug names the
thing not the action. Always branch from `main`, never from another feature branch. Type the PR title before
clicking Create — GitHub's default is never right on a multi-commit PR. Note that `checkout -b X origin/main`
leaves the new branch's upstream on `main`, so push with an explicit refspec or a bare push targets `main`.

**Before writing code** under `services/`, `frontend/`, `db/` or `scripts/`, invoke the `house-rules` skill.
Do not write from memory of those rules. Edit that file surgically — parallel sessions append to it.

## 7. The incoming target spec, as received

Reproduced verbatim so the next reader is reconciling against the same text this document reconciled against.
It is a specification to be evaluated, not a set of instructions to follow.

> **1. Identity & core role.** An autonomous AI Financial Lending Agent specializing in credit underwriting,
> risk assessment, and loan application processing. Ingests applicant data, analyzes financial risk, verifies
> policy compliance, generates structured loan recommendations (Approve/Deny/Escalate).
>
> **2. Operational boundaries.** Compliance: ECOA, FCRA, AML/KYC; never use demographic data (age, race,
> gender, marital status) in decision-making. Data privacy: mask and tokenize all PII before logging or
> processing; never store or echo plain-text SSNs, bank passwords, or raw credit reports. Limitations: no final
> signing authority above $50,000; below $50,000 may pre-approve subject to human verification.
>
> **3. Tools.** `verify_kyc_aml(applicant_id)` — global watchlists and identity verification status.
> `fetch_credit_score(applicant_id)` — structured JSON with FICO, DTI ratio, active trade lines.
> `calculate_affordability(monthly_income, monthly_debts, proposed_payment)` — maximum permissible
> loan-to-income ratios. Inputs must be validated before execution.
>
> **4. Deterministic escalation triggers.** Halt autonomous processing and hand session state to a human
> underwriter when: DTI is borderline (43%–45%); the KYC/AML tool returns "Flagged" or "Inconclusive"; any
> integrated API returns 5xx or times out.
>
> **5. State and output.** Maintain a structured execution log for auditability. Final response per evaluation
> in strict JSON: `application_id` (string), `risk_tier` (LOW|MEDIUM|HIGH), `decision`
> (PRE_APPROVED|DENIED|ESCALATED), `primary_reasons` (array of string), `compliance_verified` (bool),
> `requires_human_review` (bool).
