# Red-team pass — 2026-09-02

First issue. Scope: the LLM surface plus the money paths.

This pass binds the controls that already exist in this repo to two external control
vocabularies — the OWASP Top 10 for LLM Applications, the OWASP Top 10 for Agentic
Applications, OWASP ASVS 5.0 and OWASP AISVS 1.0 — so that
"which control holds LLM01?" has an answer that a client, an auditor, or a fresh
session can look up. It is an index-and-gap exercise, not a penetration test: no
exploitation was attempted against a running stack, and no code was changed on this
branch.

## How this file works

- One file per pass, dated. A later pass is a new file; this one is never rewritten
  to stay true, the same convention `docs/regulator-watch/` uses.
- Every claim cites `file:line` in this branch's own tree, or names the CI job that
  holds it. A claim with neither is listed under **Not graded this pass**.
- Findings here do **not** create debt-log entries. Promoting one is a separate,
  deliberate step — see **Next actions**.

## Control vocabulary

### OWASP Top 10 for LLM Applications — dual-cited

The 2026 edition (published 2026-08-04) supersedes 2025 and **renumbers most of the
list**, so a single-edition citation ages badly in either direction. This file cites
2026 as primary with the 2025 identifier alongside, because existing repo text
predates 2026.

| LLM02 | LLM02 | Sensitive Information Disclosure |
| LLM03 | LLM06 | Excessive Agency |
| LLM04 | LLM03 | Supply Chain |
| LLM05 | LLM04 | Data and Model Poisoning |
| LLM06 | LLM10 | Unbounded Consumption |
| LLM07 | LLM09 | Misinformation |

Note the two large moves: Unbounded Consumption rises from tenth to sixth, and
Improper Output Handling falls from fifth to tenth.

### ASVS 5.0 — chapters in and out of scope

ASVS 5.0 has seventeen chapters. Fourteen are in scope for this pass:

V1 Encoding and Sanitization · V2 Validation and Business Logic · V3 Web Frontend
Security · V4 API and Web Service · V6 Authentication · V7 Session Management ·
V8 Authorization · V9 Self-contained Tokens · V11 Cryptography · V12 Secure
Communication · V13 Configuration · V14 Data Protection · V15 Secure Coding and
Architecture · V16 Security Logging and Error Handling.

Out of scope, with reasons: **V5 File Handling** — the platform accepts no file
upload; **V10 OAuth and OIDC** — authentication is a server-side session in Redis,
not a delegated flow; **V17 WebRTC** — no real-time media anywhere.

### OWASP Top 10 for Agentic Applications — ASI01 to ASI10

Released 2025-12-09. This is the list that fits this repo's week-10 slice most
closely: the officer assistant is a tool-calling loop, and the general LLM list has
no row for tool misuse or for privilege abuse across a tool boundary.

Three of the ten do not apply here, and are recorded as such rather than graded:
**ASI05 Unexpected Code Execution** — no tool executes code; **ASI07 Insecure
Inter-Agent Communication** — one agent, no agent-to-agent hop; **ASI10 Rogue
Agents** — one supervised agent invoked by an officer, with no autonomous schedule.

### OWASP AISVS 1.0

ASVS 5.0 has no agentic chapter. AISVS is the separate verification standard that
does — twelve chapters, C01 through C12, version 1.0 stable. Eleven are graded
below; **C10 Model Context Protocol (MCP) Security** does not apply, as nothing here
speaks MCP.


## Method

The pass runs in six stages. R0–R2 are complete in this file. R3–R5 are not, and are
listed under **Next actions** rather than claimed.

- **R0 — freeze the vocabulary.** Pin the editions and the in-scope chapter set, as
  above. Without this, later passes grade against a moving list.
- **R1 — inventory the surface.** Enumerate the code paths in scope and record their
  size, so a later pass diffs against a frozen list rather than re-deriving one.
- **R2 — bind existing controls to identifiers.** One row per LLM identifier and per
  in-scope ASVS chapter, each carrying the code path, the test that holds it, and the
  blocking CI job. A row with a control but no test, or a test but no gate, is a
  finding before anything is attacked.
- **R3 — attack the unmapped rows only.** Each attack is an executable test that is
  watched failing first, not a prose assertion. The rows already held by a blocking
  gate are not re-attacked; that is what the gate is for.
- **R4 — route the confirmed findings.** A confirmed gap becomes a debt-log entry or
  a named residual on an existing one, using that page's Mitigated/Fixed vocabulary.
- **R5 — persist the vocabulary.** Carry the identifiers into the adversarial-review
  checklist so later reviews cite a control rather than a freehand severity.

## Findings

Six, all Low or Medium. Nothing found in this pass contradicts a control the repo
claims to have; the findings are unmapped rows and one mis-citation.

### F1 — Two code comments cite a retired OWASP edition (Low)

`services/origination-service/app/rate_limit.py:1` and
`services/origination-service/tests/test_rate_limit.py:1` both label the rate limiter
`LLM04 -- unbounded cost/DoS`. `LLM04` was Model Denial of Service in the 2023
edition. In both current editions LLM04 means something else entirely — Data and
Model Poisoning in 2025, Supply Chain in 2026 — and unbounded consumption is
LLM06:2026 / LLM10:2025. The citation is not merely stale, it now points at an
unrelated risk class.

Fix is two comment lines. The real lesson is that a bare identifier with no edition
is unmaintainable; every identifier written into this repo should carry its edition.

### F2 — The rate limiter is per-process and its residual is not on the debt log (Medium)

`app/rate_limit.py` keeps its counters in a module-level dict behind a lock. The
docstring is honest about the consequence — a restart clears it, and a second
instance would not share it. That is correct today, because nothing runs more than
one instance of origination-service.

The finding is not the design. It is that this residual exists only in a docstring:
`docs/debt-log.md` has no entry for it, so the standing answer to "what limits LLM
spend?" is not discoverable from the page a fresh session actually reads. The
per-request ceilings (`token_budget`, `max_tokens`, `_MAX_STEPS`) are real and
enforced, and they bound a single request well; nothing bounds a fleet of them once
the service scales past one instance.

### F3 — Nothing grades LLM04:2026 Supply Chain (Gap)

`redactor-drift` holds the seven redactor copies identical to each other, which is a
consistency control, not a supply-chain one. Across seven `requirements.txt` files
there is no lockfile, no hash pinning, and no dependency-vulnerability job anywhere in the
CI file. The model provider path adds a second supply chain on top of
the Python one.

This is the only row in either matrix with no control at all. Scoping it is a
separate decision — a dependency-audit job is cheap, hash-pinning seven services is
not — and it is deliberately left as a decision rather than proposed as a fix here.

### F4 — Improper output handling holds by framework default, with nothing asserting it (Low)

Model-authored text reaches the officer through `frontend/app/underwriting/[appId]/page.tsx`.
No `dangerouslySetInnerHTML`, no `innerHTML`, and no markdown-to-HTML renderer exists
anywhere under `frontend/`, so React escapes the string and LLM10:2026 is closed by
construction.

Nothing holds it closed. A future markdown renderer added for readability — the
single most likely change to that panel — would open a stored-injection path from the
policy corpus to the officer's browser, and no test or gate would notice. The cheap
close is a repository-level assertion that no raw-HTML sink exists, not a test of the
panel itself.

### F5 — The officer-facing trust surface is controlled but unasserted (Low)

ASI09 is the row the general LLM list has no equivalent for, and the controls turn
out to be real: the panel labels the output "AI assistant" rather than presenting it
as system fact, `policy_citations` is carried as a structured field rather than only
as prose the model wrote, every search attempt is recorded so an abstention is
legible as one, and a response carrying another application's id is refused before
any state write.

None of those three trust properties has an assertion. The six panel tests cover
cross-application contamination and reason completeness — both real, neither about
calibrated trust. Removing the "AI assistant" label, rendering citations only from
prose, or collapsing the abstain record would each pass every test in the file. The
`frontend` job builds the app; it does not grade this.

### F6 — No documented control over which model version runs (Gap)

AISVS C03 asks how a model version reaches production and what happens when the
provider changes it. Here the model id and its parameters are environment
configuration read in `services/origination-service/app/llm/config.py`, with a
fail-closed startup check on the values but no pinning policy, no record of which
version produced a given run beyond the trace, and no stated behaviour when the
provider retires or silently updates a model.

This matters more than it looks on a regulated path: the disclosure narration judge
and the decision assistant are both graded against fixtures produced under one model,
and nothing ties a graded pass to the version it graded.


## Not graded this pass

Named so the next pass starts from a known boundary rather than assuming coverage.

- **No live exploitation.** Nothing was run against a running stack; every verdict is
  read from source, tests, and CI job definitions.
- **The frontend beyond output handling.** V3 is graded only on the cookie flags and
  the absence of raw-HTML sinks. No CSRF, CSP, or client-side storage review.
- **`rag_eval/` as an attack surface.** Graded only where it backs LLM07. The harness
  itself, its cache, and its report path were not examined.
- **The provider account.** Bedrock IAM scope, key handling, and model-invocation
  permissions are deployment posture and were not read.
- **Prompt-level adversarial testing against a live model.** Every injection result
  cited here comes from an offline fake adapter, which is what makes those tests
  deterministic, and also what makes them a test of the boundary rather than of the
  model.
