# Regulator watch — 2026-09-01

**A recurring check on Meridian Lending's regulators.** Meridian is a consumer
personal-installment-loan lender, so the regulators that move our obligations are the
**CFPB** (Consumer Financial Protection Bureau) and the rules it administers: **Regulation B**
(ECOA — fair lending and adverse-action notices) and **Regulation Z** (TILA — APR, finance
charge, disclosures). This file records what moved this period, why it matters to us, and
what we do about it — so we can say what changed *before the client tells us*.

## How this file works

- **Cadence:** re-issued weekly at the Friday freeze, before the Monday client demo. Copy
  this file to `docs/regulator-watch/<next-Friday>.md`, refresh the findings, and delete
  nothing — an item that stopped moving becomes a one-line "no change since <date>".
- **Freshness metric (from the weeks 1–4 closure goal):** the newest
  `docs/regulator-watch/*.md` must be **≤ 7 days old at the demo**. Command:
  `ls docs/regulator-watch/*.md | tail -1` vs the demo date.
- **Sources of record:** `consumerfinance.gov/rules-policy/final-rules/`,
  `consumerfinance.gov/compliance/circulars/`, and the Federal Register CFPB index. Every
  row below is dated and linked; a claim we could not verify from a primary source is
  marked **UNVERIFIED** rather than stated as fact.
- **Scope note:** this is a lender-side watch list, not legal advice. Anything with a
  compliance deadline goes to Priya (Compliance Officer) for the actual determination;
  SOX/reconciliation questions go to Sam (Controller) — see the SOX row below.

## Watch universe — scope

The trainer's item asked for CFPB circulars + Reg B + Reg Z. That is the *minimum*. A
consumer-installment + card lender's real obligation surface is wider, so this is the full
list we watch, each mapped to the Meridian service it governs. **Active** rules get a source
check every issue; **monitor** rules are event-driven (checked when a headline or the client
raises them); **cross-cutting** is a standing enforcement lens, not a rule that "changes";
**pending applicability** means we do not yet know whether the regime binds Meridian at all,
so no sweep cadence is promised for it until that question is answered.

## New this issue — SR 11-7 model risk management (Federal Reserve / OCC)

Added because the platform makes a regulated credit decision with a model, and this file had
no row for model risk at all. The term was already in the repo before this issue — but only
once, and as a reason to *reject* an option: `adr/0009-decisioning-assistant-design.md` rejects
LLM-based scoring partly as "Ungovernable under model-risk expectations (SR 11-7)". Knowing the
standard well enough to design against it, while never tracking it, is the gap this row closes.

Applicability is genuinely open, same posture as the SOX row: SR 11-7 is supervisory guidance
for banking organizations, and Meridian is a non-bank lender. Do not treat the table below as a
compliance finding — it is a statement of where the platform stands against the three elements
SR 11-7 describes (development and implementation, validation, governance), so that whoever
makes the determination is not starting from zero.

| Control objective | Current state | Source |
|---|---|---|
| A model of record exists and is identified | **Partially met.** Every decision records the model's identity: `decision_events.decided_by` holds "model id+version, or user id for manual/override decisions" and `drivers` holds "model score, ranked attributions, band cutoff, model id+version". So per-decision identity is reconstructable. What does not exist is a model inventory as a document — no file in `docs/` or `adr/` names one. | `db/init/001_schema.sql` (`decision_events` column comments); `adr/0008-retrievable-decision-records.md` |
| The model is a validated artifact | **Not met, and deliberately so.** `services/decision-service/app/model_vendor.py` is a deterministic stand-in — `MODEL_ID = "meridian-risk-stub"` — because no licensed vendor artifact exists. Its docstring says it emits the vendor output *shape* the platform integrates against. There is no validation report, no challenger model and no backtest anywhere in the repo. | `adr/0009-decisioning-assistant-design.md` §2 |
| The implemented model matches its stated policy | **Not met — newly recorded.** The written credit policy conditions all three bands on debt-to-income as well as score; `model_vendor.policy_band()` takes the score alone, and DTI's influence floors at −80 points while the other features reach +137. Verified by executing the module: DTI 2.00 still scores 697 and bands `approve`, where the policy denies above 50%. | `docs/debt-log.md` D41; `policies/underwriting_guidelines.md` |
| Model inputs are of known quality | **Not met.** Three of the four scored features are unverified applicant assertions, and the decision record could not say which until D26 was addressed; the credit-derived feature carries an honest provenance label (`bureau_verified`, `synthetic_credit`, `synthetic_credit_bureau_failed`) held by the blocking `synthetic-credit-gate`. Labelling is not verification. | `docs/debt-log.md` D26; `services/decision-service/app/reasons.py` |
| Model output is explainable to the consumer | **Met.** `reasons.py` derives principal reasons from the model's actual ranked negative attributions and raises `UnmappedFeatureError` — refusing the decision — on any feature it cannot explain. That fail-closed rule is also the stated integration gate for a real vendor model. | `adr/0009-decisioning-assistant-design.md` §3; `services/decision-service/app/reasons.py` |
| Ongoing monitoring for performance and disparate impact | **Not met.** ADR 0016 decides that fair-lending monitoring computes outside the platform, and is **Proposed with no export code built**. Nothing measures model performance drift or disparate impact today, so the divergence recorded in D41 would not have surfaced through monitoring. | `adr/0016-fair-lending-monitoring-computes-outside-the-platform.md` |
| Governance over the LLM-assisted surface | **Partially met.** The officer assistant cannot decision an application — the regulated decision happens inside the score tool and its append-only record — and its runs are recorded in `assistant_runs` behind the blocking `assistant-telemetry-gate`, exported only through an officer-gated metrics route. What is absent is any documented owner, review cadence or change-control for the model itself. | `adr/0021-agent-framework-and-root-trace.md`; `services/origination-service/app/assistant.py` |
